1. The entire system in one picture

The project is a modular monolith. One Spring Boot deployment contains feature modules. PostgreSQL is durable truth. Redis coordinates fast/temporary work. Active battles use in-memory sessions for the hot path.

Angular ClientREST + STOMP

→
Feature modulesauth · player · card · matchmaking · game
→
State layerPostgres · Redis · GameSession memory

REST Setup & CRUD

Register/login, profile, card catalog, deck, history, matchmaking commands, leaderboard reads.

WebSocket Live battle

Match-found push, moves, turn events, timers, round results, reconnect snapshots, game-over.

Postgres Durable truth

Players, cards, ownership, completed games and rounds. Flyway alone changes schema.

Redis Coordination

Card cache, matchmaking queue, SETNX idempotency, expiring room codes, sorted-set leaderboard.

Memory Hot game state

ConcurrentHashMap<UUID, GameSession>. One lock per game. No DB call for every move.

Architecture rule

Controller → Service → Repository. DTOs cross boundaries; entities do not. Transactions belong to services.

2. How you should think before writing a class

Question A — Is this durable?

If losing it on Redis restart/server crash is unacceptable, Postgres must own it.

Question B — Is this live?

If the server must push without the client polling, it belongs in WebSocket/STOMP.

Question C — Can two requests race?

If yes, identify the invariant first, then choose DB versioning, Redis atomicity, or a per-session lock.

Question D — Which layer owns the rule?

Shape validation = DTO. Auth = security. Ownership/turn legality = service/validator. Persistence = repository.

06

Matchmaking — your first distributed concurrency problem

Two players must be paired exactly once even when requests hit concurrently.

Quick match

SETNX player guard → LPUSH queue → scheduled RPOP pairing → create game/session → private MatchFoundEvent.

Private room

Create code with TTL → Lua script atomically checks vacancy + claims second slot → notify both players.

Learn nowRedis List producer/consumer, SETNX idempotency, TTL state, Lua atomicity, scheduler semantics.
Concurrency proofUse Testcontainers + CountDownLatch. Ten simultaneous joins to one room must produce exactly one successful second player.
07

Game Engine — build correctness before cleverness

This is the core. Active state is in memory, mutation is serialized per game, and every client claim is revalidated.

Build order

GameEvent hierarchy → Move/GameState DTOs → immutable CardRef → GameSession → MoveValidator → TurnTimer → GameEngine → GameSessionManager → GameService → GameSocketController → metrics.

Learn nowState machines, synchronized/per-session locks, ConcurrentHashMap, ScheduledExecutorService, stale-version rejection, reconnect lifecycle.
Exit testTwo simultaneous moves cannot corrupt state. Wrong turn/card/version is rejected. Timer expiry races with a move safely. Finished game persists once.
Core invariantOnly one writer mutates a specific GameSession at a time. Never hold that lock while doing DB/network I/O.

Runtime stories — follow these instead of memorizing classes

Story A · New player registers
POST register → DTO validation → AuthService transaction → unique player → BCrypt hash → save Player → grant 10 PlayerCard rows → issue JWT + refresh token → commit. Any failure rolls the entire registration back.
Story B · Player clicks Quick Match twice
First request wins Redis SETNX and enters queue. Second request sees the guard and cannot duplicate the player. Scheduler removes two distinct waiting players, creates a game, then pushes MatchFoundEvent privately over STOMP.
Story C · Two users join the same private room simultaneously
Both reach Redis, but the Lua script executes atomically. Only one can claim the second-player slot. The loser receives conflict; this is proven with a concurrent Testcontainers test.
Story D · Player sends a battle move
STOMP handler identifies authenticated player → GameSessionManager gets session → GameEngine enters per-session critical section → MoveValidator checks player, turn, card, stat and stateVersion → mutate state + increment version → leave lock → publish events/persist as appropriate.
Story E · Player disconnects and reconnects
Disconnect event marks connection state and starts grace timer, not immediate forfeit. Reconnect re-associates player and sends full GameStateDTO snapshot so the client can recover from missed events.

Definition of done — when the backend is actually portfolio-ready

  • Fresh clone boots with one documented command.
  • Flyway owns schema and Testcontainers runs the same migrations.
  • JWT access/refresh/logout lifecycle is tested.
  • REST contract is consistent and entities never leak.
  • Redis's five roles are explicit and independently explainable.
  • WebSocket authentication, private destinations and broadcast destinations are tested.
  • Quick-match and room-join races have concurrency proofs.
  • Game session has a single-writer invariant and stale-version rejection.
  • Disconnect/reconnect sends a full authoritative snapshot.
  • Completed game + player stats update transactionally.
  • Leaderboard is rebuildable from durable data.
  • You can explain single-instance limitations and the horizontal-scaling upgrade path.
  • CI runs mvn verify against real Postgres/Redis containers.
