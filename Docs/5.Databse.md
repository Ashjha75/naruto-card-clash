# Naruto Card Clash — Database Design

Phase 2 of `BACKEND-SETUP.md`. This is the authoritative schema — it
consolidates every decision made across the earlier docs (audit columns,
`@Version`, the `UNIQUE(game_id, round_number)` constraint, indexes) into
one correct, final version. If `V1__init.sql` in your repo doesn't match
this yet, this doc wins.

---

## 1. Entity-Relationship Diagram

```
players ──1────< player_cards >────1── cards
   │
   ├──< games.player1_id
   ├──< games.player2_id
   ├──< games.winner_id            (nullable — null until decided)
   │
   ├──< game_rounds.attacker_id
   └──< game_rounds.winner_id      (nullable — null on a tie)

games ──1────< game_rounds

game_rounds >──── cards.attacker_card_id
game_rounds >──── cards.defender_card_id
```

Two entities have more than one foreign key pointing at the same target
table — `games` has three separate relationships to `players`
(`player1_id`, `player2_id`, `winner_id`), and `game_rounds` has two to
`players` and two to `cards`. That's not a modeling mistake; it's just what
"two players, each with a card, one of them wins" actually requires. It
matters later because Hibernate needs each relationship named explicitly —
see §5.

## 2. Full Schema

```sql
-- V1__init.sql

CREATE TABLE players (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    username      VARCHAR(30) UNIQUE NOT NULL,
    email         VARCHAR(100) UNIQUE NOT NULL,
    password_hash VARCHAR(255) NOT NULL,
    avatar_url    VARCHAR(500),
    xp            INTEGER NOT NULL DEFAULT 0,
    level         INTEGER NOT NULL DEFAULT 1,
    total_wins    INTEGER NOT NULL DEFAULT 0,
    total_losses  INTEGER NOT NULL DEFAULT 0,
    total_draws   INTEGER NOT NULL DEFAULT 0,
    created_at    TIMESTAMP NOT NULL DEFAULT NOW(),
    created_by    UUID,
    updated_at    TIMESTAMP NOT NULL DEFAULT NOW(),
    updated_by    UUID,
    version       INTEGER NOT NULL DEFAULT 0
);

CREATE TABLE cards (
    id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name       VARCHAR(50) NOT NULL,
    image_url  VARCHAR(500),
    attack     INTEGER NOT NULL CHECK (attack  BETWEEN 1 AND 100),
    defense    INTEGER NOT NULL CHECK (defense BETWEEN 1 AND 100),
    chakra     INTEGER NOT NULL CHECK (chakra  BETWEEN 1 AND 100),
    speed      INTEGER NOT NULL CHECK (speed   BETWEEN 1 AND 100),
    rarity     VARCHAR(20) NOT NULL CHECK (rarity IN ('COMMON','RARE','LEGENDARY')),
    village    VARCHAR(50),
    created_at TIMESTAMP NOT NULL DEFAULT NOW(),
    created_by UUID,          -- NULL for Flyway-seeded rows, no player created these
    updated_at TIMESTAMP NOT NULL DEFAULT NOW(),
    updated_by UUID,
    version    INTEGER NOT NULL DEFAULT 0
);

CREATE TABLE player_cards (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    player_id   UUID NOT NULL REFERENCES players(id),
    card_id     UUID NOT NULL REFERENCES cards(id),
    obtained_at TIMESTAMP NOT NULL DEFAULT NOW(),
    created_at  TIMESTAMP NOT NULL DEFAULT NOW(),
    created_by  UUID,
    updated_at  TIMESTAMP NOT NULL DEFAULT NOW(),
    updated_by  UUID,
    version     INTEGER NOT NULL DEFAULT 0,
    UNIQUE(player_id, card_id)
);

CREATE TABLE games (
    id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    player1_id   UUID NOT NULL REFERENCES players(id),
    player2_id   UUID NOT NULL REFERENCES players(id),
    winner_id    UUID REFERENCES players(id),
    game_type    VARCHAR(20) NOT NULL CHECK (game_type IN ('QUICK_MATCH','PRIVATE_ROOM')),
    room_code    VARCHAR(10),
    total_rounds INTEGER NOT NULL,
    status       VARCHAR(20) NOT NULL CHECK (status IN ('WAITING','IN_PROGRESS','FINISHED','ABANDONED')),
    started_at   TIMESTAMP NOT NULL DEFAULT NOW(),
    ended_at     TIMESTAMP,
    created_at   TIMESTAMP NOT NULL DEFAULT NOW(),
    created_by   UUID,
    updated_at   TIMESTAMP NOT NULL DEFAULT NOW(),
    updated_by   UUID,
    version      INTEGER NOT NULL DEFAULT 0    -- load-bearing: this is the optimistic lock from ARCHITECTURE.md §6
);

CREATE TABLE game_rounds (
    id               UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    game_id          UUID NOT NULL REFERENCES games(id),
    round_number     INTEGER NOT NULL,
    attacker_id      UUID NOT NULL REFERENCES players(id),
    attacker_card_id UUID NOT NULL REFERENCES cards(id),
    defender_card_id UUID NOT NULL REFERENCES cards(id),
    chosen_stat      VARCHAR(20) NOT NULL CHECK (chosen_stat IN ('ATTACK','DEFENSE','CHAKRA','SPEED')),
    attacker_value   INTEGER NOT NULL,
    defender_value   INTEGER NOT NULL,
    winner_id        UUID REFERENCES players(id),   -- NULL on a tie
    played_at        TIMESTAMP NOT NULL DEFAULT NOW(),
    created_at       TIMESTAMP NOT NULL DEFAULT NOW(),
    created_by       UUID,
    updated_at       TIMESTAMP NOT NULL DEFAULT NOW(),
    updated_by       UUID,
    version          INTEGER NOT NULL DEFAULT 0,
    UNIQUE(game_id, round_number)   -- the idempotency guard from BACKEND-SETUP.md §5
);

CREATE INDEX idx_player_cards_player ON player_cards(player_id);
CREATE INDEX idx_player_cards_card   ON player_cards(card_id);
CREATE INDEX idx_games_player1       ON games(player1_id);
CREATE INDEX idx_games_player2       ON games(player2_id);
CREATE INDEX idx_games_status        ON games(status);
CREATE INDEX idx_game_rounds_game    ON game_rounds(game_id);
CREATE INDEX idx_cards_rarity        ON cards(rarity);
CREATE INDEX idx_cards_village       ON cards(village);
```

**Why `VARCHAR` + `CHECK` instead of a native Postgres `ENUM` type** for
`status`, `game_type`, `chosen_stat`, `rarity`: a native `ENUM` is stricter,
but adding a new value later means `ALTER TYPE ... ADD VALUE`, which is
more awkward to script and historically couldn't run inside the same
transaction as other DDL. `VARCHAR` + `CHECK` is exactly as strict at the
row level, evolves with a plain migration, and is what Hibernate's
`@Enumerated(EnumType.STRING)` naturally writes anyway — no mismatch
between what Java sends and what the column expects.

## 3. Indexing Strategy

**Postgres does not automatically index foreign key columns** — unlike
MySQL, an `FK REFERENCES` constraint alone gives you referential integrity,
not a lookup index. Every FK column you'll actually query by needs an
explicit `CREATE INDEX`, which is why the list above isn't just "index the
primary keys."

| Index                                     | Query it serves                                                                                                                                                                                      |
| ----------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `idx_player_cards_player`                 | "Give me this player's cards" — hot, hit on every profile/collection view                                                                                                                            |
| `idx_player_cards_card`                   | Needed for the FK itself; also serves "who owns this card" if ever queried                                                                                                                           |
| `idx_games_player1` / `idx_games_player2` | Match history — a player can be in either column, so a history query is `WHERE player1_id = ? OR player2_id = ?` and needs both indexes to avoid a sequential scan on either side                    |
| `idx_games_status`                        | Ops/debugging queries like "how many games are IN_PROGRESS" — not the hot path (that's `GameSessionManager` in memory, see `ARCHITECTURE.md` §5), this is for when you need to ask Postgres directly |
| `idx_game_rounds_game`                    | "Give me all rounds for this game" — match replay / detail view, hot                                                                                                                                 |
| `idx_cards_rarity` / `idx_cards_village`  | Card catalog filters                                                                                                                                                                                 |

Honest caveat on the last two: `cards` has ~30 rows. Postgres will likely
sequential-scan a 30-row table regardless of the index — the planner isn't
wrong to do that, an index only wins once a scan is more expensive than an
index lookup. These indexes are correct practice and matter if the catalog
grows past a few hundred rows; at 30 rows they're basically free insurance,
not a performance requirement yet. Know the difference between "correct"
and "currently necessary."

**Verifying an index is actually used:**

```sql
EXPLAIN ANALYZE SELECT * FROM player_cards WHERE player_id = '...';
```

Look for `Index Scan using idx_player_cards_player` in the output, not
`Seq Scan`. This is the concrete way to confirm an index earns its place
instead of assuming it does.

## 4. JPA Entity Mapping

### BaseEntity — every entity below extends this

```java
@MappedSuperclass
@EntityListeners(AuditingEntityListener.class)
public abstract class BaseEntity {

    @Id @GeneratedValue
    private UUID id;

    @CreatedDate
    @Column(name = "created_at", updatable = false)
    private Instant createdAt;

    @CreatedBy
    @Column(name = "created_by", updatable = false)
    private UUID createdBy;

    @LastModifiedDate
    @Column(name = "updated_at")
    private Instant updatedAt;

    @LastModifiedBy
    @Column(name = "updated_by")
    private UUID updatedBy;

    @Version
    private Integer version;
}
```

### Player

```java
@Entity
@Table(name = "players")
public class Player extends BaseEntity {

    @Column(unique = true, nullable = false, length = 30)
    private String username;

    @Column(unique = true, nullable = false, length = 100)
    private String email;

    @Column(name = "password_hash", nullable = false)
    private String passwordHash;

    private String avatarUrl;
    private Integer xp = 0;
    private Integer level = 1;
    private Integer totalWins = 0;
    private Integer totalLosses = 0;
    private Integer totalDraws = 0;

    @OneToMany(mappedBy = "player", fetch = FetchType.LAZY)
    private List<PlayerCard> cards;
}
```

### Card

```java
@Entity
@Table(name = "cards")
public class Card extends BaseEntity {

    private String name;
    private String imageUrl;
    private Integer attack;
    private Integer defense;
    private Integer chakra;
    private Integer speed;

    @Enumerated(EnumType.STRING)
    private Rarity rarity;

    private String village;
}
```

### PlayerCard — the junction entity

```java
@Entity
@Table(name = "player_cards",
       uniqueConstraints = @UniqueConstraint(columnNames = {"player_id", "card_id"}))
public class PlayerCard extends BaseEntity {

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "player_id", nullable = false)
    private Player player;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "card_id", nullable = false)
    private Card card;

    private Instant obtainedAt;
}
```

### Game — three relationships to the same entity type

```java
@Entity
@Table(name = "games")
public class Game extends BaseEntity {

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "player1_id", nullable = false)
    private Player player1;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "player2_id", nullable = false)
    private Player player2;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "winner_id")
    private Player winner;                    // nullable — not decided until the game ends

    @Enumerated(EnumType.STRING)
    private GameType gameType;

    private String roomCode;
    private Integer totalRounds;

    @Enumerated(EnumType.STRING)
    private GameStatus status;

    private Instant startedAt;
    private Instant endedAt;
    // version, createdAt, etc. inherited from BaseEntity
}
```

### GameRound — two relationships each to Player and Card

```java
@Entity
@Table(name = "game_rounds",
       uniqueConstraints = @UniqueConstraint(columnNames = {"game_id", "round_number"}))
public class GameRound extends BaseEntity {

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "game_id", nullable = false)
    private Game game;

    private Integer roundNumber;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "attacker_id", nullable = false)
    private Player attacker;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "attacker_card_id", nullable = false)
    private Card attackerCard;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "defender_card_id", nullable = false)
    private Card defenderCard;

    @Enumerated(EnumType.STRING)
    private Stat chosenStat;

    private Integer attackerValue;
    private Integer defenderValue;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "winner_id")
    private Player winner;                    // nullable — null on a tie

    private Instant playedAt;
}
```

## 5. The Multiple-FK-to-Same-Entity Gotcha

`Game` has three `@ManyToOne` fields all pointing at `Player`
(`player1`, `player2`, `winner`), and `GameRound` has two each pointing at
`Player` and `Card`. This is where people new to JPA get a confusing error
or an accidentally-shared mapping, because the default relationship naming
Hibernate would infer only works when there's exactly one relationship to a
given target type.

The fix is what's already in the code above: **always give `@JoinColumn` an
explicit `name`** when there's more than one relationship to the same
entity. Never rely on Hibernate's default column-naming guess in this
situation — name every one of them yourself.

## 6. Migrations (Flyway)

- **Naming convention:** `V{version}__{description}.sql` — double
  underscore is required, not stylistic. `V1__init.sql`, `V2__seed_cards.sql`.
- **Immutability rule:** once a migration has run anywhere (even just your
  own machine), never edit it. Flyway checksums every applied migration; an
  edited file fails validation on the next run. If you got something wrong,
  write `V3__fix_x.sql` — you don't rewrite history.
- **No automatic rollback.** Unlike some framework migration tools, Flyway
  doesn't ship an automatic "down" migration. Undoing a bad migration means
  writing a new forward migration that reverses it. Know this going in —
  it changes how carefully you write V1.
- **Tracking table:** Flyway creates and maintains `flyway_schema_history`
  itself — one row per applied migration, with its checksum. That's how it
  knows what's already run.
- **`ddl-auto: validate`, not `update`:** Hibernate checks that your entity
  mappings match what Flyway already created — it will fail startup loudly
  if they've drifted, but it will never generate or alter schema itself.
  Flyway is the only thing allowed to change the schema.
- **`V2__seed_cards.sql`:** the 30 Naruto cards, inserted as data-only SQL,
  not through a `CommandLineRunner`. Versioned and repeatable like any
  other migration, and it runs exactly once — Flyway won't re-insert on
  every restart.
- **Test profile:** Flyway runs the exact same migrations against the
  Testcontainers Postgres instance in tests — see §9.

## 7. Concurrency & Locking

Every table has a `version` column via `BaseEntity`, but it's not equally
load-bearing everywhere:

| Table                         | Is `@Version` actually doing work here?                                                                                                                                                                                                                                                                                                                                                     |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `games`                       | Yes — this is the exact mechanism from `ARCHITECTURE.md` §6 preventing lost updates when concurrent round-processing touches the same game row                                                                                                                                                                                                                                              |
| `players`                     | Sometimes — but for a simple counter bump like `total_wins`, an atomic `UPDATE players SET total_wins = total_wins + 1 WHERE id = ?` is simpler and doesn't need optimistic locking at all, since the increment happens in a single SQL statement with no read-modify-write gap. `@Version` matters more here if you're updating several fields together based on a value you read earlier. |
| `cards`                       | Rarely — admin-only writes, low contention                                                                                                                                                                                                                                                                                                                                                  |
| `player_cards`, `game_rounds` | Effectively append-only after creation — the `UNIQUE` constraint on `game_rounds` is what's actually protecting it, not the version column                                                                                                                                                                                                                                                  |

**When you'd reach for pessimistic locking instead** (`SELECT ... FOR
UPDATE`): when you need to guarantee no one else can even _read_ a row for
update purposes while you're mid-transaction — useful for something like a
"claim this reward exactly once" flow with a longer transaction. Nothing in
this schema currently needs it; know the trade-off (it blocks, optimistic
locking doesn't) rather than defaulting to it out of caution.

## 8. Transactions

`@Transactional` boundaries live in the service layer, never the
controller (see `ARCHITECTURE.md` §2). The two that matter most:

- **`AuthService.register()`** — create the `Player` row and grant the
  starter deck (10 `PlayerCard` rows) must both succeed or both roll back.
  A player should never exist without their starter deck.
- **`GameService.finishGame()`** — persist the final `Game`/`GameRound`
  rows and update the winner/loser's `total_wins`/`total_losses` together.
  A completed match should never be recorded without the stats update
  landing too.

Default propagation (`REQUIRED`) and Postgres's default isolation level
(Read Committed) are both left as-is — nothing in this schema's access
patterns needs a stricter isolation level, and reaching for one
unnecessarily just adds contention.

## 9. Connection Pooling

HikariCP, Spring Boot's default pool, configured in `application.yaml`:

```yaml
spring:
    datasource:
        hikari:
            maximum-pool-size: 10
            minimum-idle: 5
            connection-timeout: 20000
```

Why this matters: establishing a raw Postgres connection is expensive
(TCP handshake, auth, session setup), and Postgres itself has a hard
`max_connections` ceiling — a pool reuses a small set of already-open
connections instead of opening one per request. Sizing it too high just
shifts the bottleneck to Postgres's own connection limit; too low and
requests queue waiting for a free connection. 10/5 is a reasonable default
for this project's scale, not a number to treat as sacred.

## 10. Data Type Decisions

- **UUID primary keys**, not auto-increment integers. Trade-off, stated
  plainly: UUIDs can't be enumerated or guessed (`/api/players/1`,
  `/api/players/2`... doesn't work as an attack), generate client-side if
  ever needed, and merge cleanly across environments — at the cost of a
  larger index (16 bytes vs 4/8) and no natural insertion ordering.
- **`TIMESTAMP`, not `DATE`** — every time-tracking column needs to know
  _when_, not just _which day_; round timing, match duration, and token
  expiry all depend on sub-day precision.
- **`VARCHAR(n)` with real lengths, not `TEXT` everywhere** — `username
VARCHAR(30)`, `email VARCHAR(100)` documents the actual constraint at the
  schema level instead of only in application-layer validation. Defense in
  depth, same principle as the `CHECK` constraints in §2.

## 11. Deliberate Denormalization

`players.total_wins` / `total_losses` / `total_draws` are stored directly
on the row, not computed on the fly with `COUNT(*)` over `games`. This is
denormalization on purpose: showing a player's profile would otherwise mean
scanning their entire match history every time the profile loads. The
trade-off is real — these columns can drift from the truth if a stats
update is ever missed — which is exactly why §8 makes the game-finish +
stats-update transaction atomic. Know that you made this trade
deliberately, not that you forgot to normalize.

## 12. Testing the Database Layer

- `@DataJpaTest` for repository-slice tests — fast, no full Spring context.
- Full integration tests use **Testcontainers**, not H2. Flyway runs the
  real migrations against the real Postgres container, so what's under
  test is the actual schema, not an approximation of it — an H2-based test
  can pass while the real Postgres schema behaves differently (different
  `CHECK` constraint handling, different default behaviors).
- `TestcontainersConfig` (from `FOLDER-STRUCTURE.md`) is the shared base —
  one container startup, reused across the test classes that need it.

## 13. Query Patterns This Schema Needs to Support Well

A quick sanity check against real usage — every index and constraint above
exists because of one of these:

| Pattern                                 | Backed by                                                                                                                                                                |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| "My card collection"                    | `idx_player_cards_player`                                                                                                                                                |
| "My match history" (paginated)          | `idx_games_player1` / `idx_games_player2`                                                                                                                                |
| "Replay/detail of one game"             | `idx_game_rounds_game`                                                                                                                                                   |
| "Filter card catalog by rarity/village" | `idx_cards_rarity` / `idx_cards_village`                                                                                                                                 |
| "Is this username/email taken"          | the `UNIQUE` constraints on `players`                                                                                                                                    |
| "Leaderboard"                           | **not this table directly** — Redis Sorted Set is the read path (`ARCHITECTURE.md` §8); `players.total_wins` is the source that feeds `ZADD`, not what gets queried live |
