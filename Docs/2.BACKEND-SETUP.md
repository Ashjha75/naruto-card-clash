## 2. Docker Setup (from your compose.yaml)

```
postgres: postgres:17-alpine   healthcheck: pg_isready        volume: postgres-data
redis:    redis:8-alpine       healthcheck: redis-cli ping    volume: redis-data   --appendonly yes
```

This is solid as-is: named containers, healthchecks with `start_period`,
persistent volumes, AOF enabled on Redis. No fixed host ports — Docker
assigns a random free port, and `spring-boot-docker-compose` reads the
actual bound port at app startup and wires `spring.datasource.*` /
`spring.data.redis.*` for you. That's why you don't (and shouldn't) hand-write
those connection properties in `application.yaml` for local dev.

Not a bug, just a decision to make: you're on `postgres:17-alpine`.
`postgres:18.4-alpine` is the current stable major if you want to move up —
17 is still fully supported, so this is optional, not required.

## 3. Fix Required: `application.yaml` indentation

Current file nests `jpa`, `flyway`, `cache` under `spring.docker` instead of
directly under `spring`, and nests `server`, `logging`, `management` under
`spring` instead of at the document root. As written, `spring.jpa.*`,
`spring.flyway.*`, `spring.cache.*`, `server.port`, `logging.level.*`, and
`management.*` are not being read — Spring Boot never looks for properties
at those paths.

Corrected:

```yaml
spring:
    application:
        name: naruto-card-clash-server

    docker:
        compose:
            file: compose.yaml # optional — auto-detected in the working dir even without this line

    jpa:
        open-in-view: false
        hibernate:
            ddl-auto: validate
        properties:
            hibernate:
                format_sql: true

    flyway:
        enabled: true
        locations: classpath:db/migration

    cache:
        type: redis
        redis:
            time-to-live: 30m
            cache-null-values: false

server:
    port: 8080

logging:
    level:
        org.springframework.security: INFO
        org.hibernate.SQL: INFO

management:
    endpoints:
        web:
            exposure:
                include: health,info
    endpoint:
        health:
            show-details: when-authorized
```

**Verify:** start the app, `GET http://localhost:8080/actuator/health` should
return `200` with `{"status":"UP"}`. That alone won't prove `server.port` is
fixed, since 8080 is also the framework default — to actually confirm it,
temporarily set `server.port: 9090` and check the app comes up on 9090
instead.

## 4. Build Phases

implementation — that comes when we build each module.

## 5. Backend Concerns Checklist

These aren't Spring-specific — they're the concerns any backend system has
to answer, regardless of framework. Table below is honest about status:
**done** means a phase above already covers it, **gap** means it's a real
hole nothing above addresses yet.

| Concern                           | What it means                                                                     | How this project handles it                                                                                                                                                         | Status                                                                   |
| --------------------------------- | --------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| Authentication                    | Proving who's making the request                                                  | Stateless JWT — access + refresh tokens                                                                                                                                             | Phase 3                                                                  |
| Authorization                     | Deciding what an authenticated identity may do                                    | Route rules + `@PreAuthorize` in `SecurityConfig`; domain-level checks (do you own this card, is it your turn) in `MoveValidator`                                                   | Phase 3 (route-level), Phase 7 (domain-level)                            |
| Input validation                  | Rejecting malformed requests before they reach business logic                     | Bean Validation (`@Valid`) on every DTO                                                                                                                                             | Phase 3–8                                                                |
| Error handling                    | Consistent, safe error responses instead of stack traces or silent failures       | `GlobalExceptionHandler` + `ApiResponse` envelope                                                                                                                                   | Phase 1                                                                  |
| Logging                           | Being able to reconstruct what happened after the fact                            | `logback-spring.xml`, structured logs tagged with `gameId`/`correlationId`                                                                                                          | Not yet in any phase — add in Phase 1                                    |
| Caching                           | Not redoing expensive/repeated work for stable data                               | `@Cacheable` cache-aside on the card catalog, Redis-backed                                                                                                                          | Phase 4                                                                  |
| Rate limiting                     | Protecting the system from abuse or accidental overload                           | Fixed-window counter (Redis `INCR`+`EXPIRE`) on IP — has a known burst flaw right at the window boundary; sliding window or token bucket is the fix if it ever matters              | Not yet in any phase — gap                                               |
| Concurrency control               | Correctness when multiple requests touch the same data at once                    | Optimistic versioning (`stateVersion`, JPA `@Version`), single-writer-per-game lock, Redis `SETNX`/Lua for cross-request coordination                                               | Phase 6–7                                                                |
| Idempotency                       | Making retries safe instead of duplicating side effects                           | `SETNX` matchmaking guard, `UNIQUE(game_id, round_number)`                                                                                                                          | Phase 6–7                                                                |
| Testing                           | Proving correctness, including under concurrency, not just on the happy path      | JUnit 5, Mockito, Testcontainers, dedicated concurrency-proof tests                                                                                                                 | Phase 6, 7, 9                                                            |
| Observability / monitoring        | Knowing what the system is doing in production, not just in a debugger            | Actuator health/metrics, Micrometer gauges (`active_games`, `matchmaking_queue_depth`)                                                                                              | Partially — Actuator is in the pom, custom metrics not yet built         |
| Configuration management          | Environment-specific behavior without code changes, secrets out of source control | Spring profiles (dev/test/prod), env-var-driven secrets                                                                                                                             | Phase 1                                                                  |
| Real-time communication           | Server-initiated push instead of client polling                                   | WebSocket/STOMP                                                                                                                                                                     | Phase 5, 7                                                               |
| Message queuing                   | Decoupling producer and consumer, async work                                      | Redis List as the matchmaking queue (producer-consumer)                                                                                                                             | Phase 6                                                                  |
| API design / contracts            | A predictable, parseable interface                                                | REST conventions, `ApiResponse` envelope, a fixed named set of WebSocket event types                                                                                                | Phase 1 onward                                                           |
| Pagination                        | Never returning an unbounded result set                                           | `Pageable`/`Page<T>` on the card catalog and match history                                                                                                                          | Phase 4                                                                  |
| Audit trail                       | Knowing who changed what, and when                                                | `createdBy`/`updatedBy` via `BaseEntity` + Spring Data JPA auditing                                                                                                                 | Phase 1                                                                  |
| Resilience / graceful degradation | Surviving partial failure instead of cascading it                                 | Cache-aside falls through to Postgres on a Redis miss; WebSocket reconnect grace period instead of instant forfeit                                                                  | Phase 4, 7                                                               |
| CORS                              | Controlling which origins may call this API                                       | **Not configured anywhere yet.** Needed the moment the Angular dev server (different origin) starts calling this API — add a `CorsConfig` bean before Phase 10 frontend work starts | Gap                                                                      |
| Compression                       | Reducing response payload size over the wire                                      | `server.compression.enabled` in `application.yaml`                                                                                                                                  | Not yet set — trivial addition to Phase 1                                |
| Graceful shutdown                 | Not killing in-flight requests or open WebSocket connections on deploy/restart    | `server.shutdown: graceful` — matters here specifically because an active game shouldn't be severed mid-round                                                                       | Not yet set — gap                                                        |
| API documentation                 | A machine-readable contract for anyone consuming this API                         | Not set up — no OpenAPI/Swagger dependency in the current pom                                                                                                                       | Optional — add `springdoc-openapi-starter-webmvc-ui` if/when it's needed |

The three real gaps worth fixing early rather than late: **CORS** (blocks
the frontend outright once you get to Phase 10), **rate limiting** (currently
just a named intention, no code), and **graceful shutdown** (cheap to turn
on, meaningfully protects live games during a deploy).
