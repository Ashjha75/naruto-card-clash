# Naruto Card Clash — API Contract

Exact request/response shapes for every REST endpoint and every WebSocket
message. This is what you code the controller against on the backend and
what the frontend codes against later — if backend and frontend ever
disagree, this doc is wrong and gets fixed, not the other way around.

---

## Conventions

- All JSON fields are `camelCase`.
- Every REST response is wrapped in the standard envelope from
  `common/dto/ApiResponse.java`:
    ```json
    { "success": true, "data": {/* ... */}, "error": null }
    ```
    On failure:
    ```json
    {
    	"success": false,
    	"data": null,
    	"error": { "code": "INVALID_MOVE", "message": "..." }
    }
    ```
    Every example below shows just the `data` payload unless the full
    envelope matters for that example.
- Auth: `Authorization: Bearer <accessToken>` header on every route except
  `register`, `login`, `refresh`.
- Paginated list endpoints return `common/dto/PageResponse.java`:
    ```json
    {
    	"content": [/* items */],
    	"page": 0,
    	"size": 20,
    	"totalElements": 137,
    	"totalPages": 7
    }
    ```
    wrapped inside `data` as usual.
- Status codes mean something: `200` read/update ok, `201` created, `202`
  accepted but not yet resolved (matchmaking), `204` no content (logout),
  `400` malformed request, `401` not authenticated, `403` authenticated but
  not allowed, `404` not found, `409` conflict (room full, username taken).

## Auth

### `POST /api/auth/register`

```json
// request  (RegisterRequest)
{
	"username": "kakashi99",
	"email": "kakashi@leaf.com",
	"password": "min8chars"
}
```

```json
// response 201  (AuthResponse)
{
	"success": true,
	"data": {
		"accessToken": "eyJhbGciOi...",
		"refreshToken": "9f2a...opaque",
		"expiresIn": 900,
		"player": { "id": "uuid", "username": "kakashi99" }
	},
	"error": null
}
```

Triggers the starter-deck grant transactionally — see `DATABASE.md` §8.

### `POST /api/auth/login`

```json
// request  (LoginRequest)
{ "email": "kakashi@leaf.com", "password": "min8chars" }
```

Response: same `AuthResponse` shape as register, `200`.

### `POST /api/auth/refresh`

```json
// request  (RefreshTokenRequest)
{ "refreshToken": "9f2a...opaque" }
```

Response: new `AuthResponse` with rotated tokens, `200`. Old refresh token
is invalidated in the same call — see `RefreshTokenService`.

### `POST /api/auth/logout`

```json
// request  (RefreshTokenRequest)
{ "refreshToken": "9f2a...opaque" }
```

`204 No Content`. Revokes the refresh token and blacklists the current
access token's `jti`.

### `GET /api/auth/me`

No body. Returns `PlayerDTO`, `200`.

## Player

### `GET /api/players/me`

```json
// response  (PlayerDTO)
{
	"id": "uuid",
	"username": "kakashi99",
	"avatarUrl": null,
	"xp": 120,
	"level": 2,
	"totalWins": 8,
	"totalLosses": 3,
	"totalDraws": 1,
	"createdAt": "2026-07-01T10:00:00Z"
}
```

`email` is deliberately **not** in `PlayerDTO` — it's PII, not needed for
any gameplay display, and only ever returned once at register/login inside
`AuthResponse`.

### `GET /api/players/{id}`

Same `PlayerDTO` shape — this is the public profile view, identical fields,
just for someone else's ID.

### `PUT /api/players/me`

```json
// request  (PlayerProfileUpdateRequest)
{ "avatarUrl": "https://..." }
```

Response: updated `PlayerDTO`, `200`.

### `GET /api/players/me/cards?page=0&size=20`

`PageResponse<CardDTO>` — see Card section for `CardDTO` shape.

### `GET /api/players/me/history?page=0&size=20`

```json
// PageResponse<GameSummaryDTO>
{
	"content": [
		{
			"gameId": "uuid",
			"opponentUsername": "gaara_of_the_desert",
			"result": "WIN",
			"cardsWon": 3,
			"cardsLost": 2,
			"playedAt": "2026-07-15T18:22:00Z"
		}
	],
	"page": 0,
	"size": 20,
	"totalElements": 12,
	"totalPages": 1
}
```

`result` is one of `WIN` / `LOSS` / `DRAW`, computed server-side by
comparing `winnerId` against the requesting player's ID — never trust a
client-supplied result.

## Card

### `GET /api/cards?rarity=LEGENDARY&village=Konoha&page=0&size=20`

`rarity` and `village` are optional filters.

```json
// PageResponse<CardDTO>, one item shown
{
	"id": "uuid",
	"name": "Kakashi Hatake",
	"imageUrl": "https://...",
	"attack": 88,
	"defense": 75,
	"chakra": 85,
	"speed": 90,
	"rarity": "LEGENDARY",
	"village": "Konoha"
}
```

### `GET /api/cards/{id}`

Single `CardDTO`, same shape, `200`.

### `POST /api/cards` — admin only, `@PreAuthorize("hasRole('ADMIN')")`

```json
// request  (CardCreateRequest)
{
	"name": "New Character",
	"imageUrl": "https://...",
	"attack": 70,
	"defense": 70,
	"chakra": 70,
	"speed": 70,
	"rarity": "RARE",
	"village": "Konoha"
}
```

Response: created `CardDTO`, `201`. `@CacheEvict` fires here — see
`ARCHITECTURE.md` §8.

### `POST /api/players/me/deck`

```json
// request  (DeckSelectionRequest)
{ "cardIds": ["uuid1", "uuid2", "uuid3", "uuid4", "uuid5"] }
```

`200` on success. `409` if any `cardId` isn't actually owned by the
requesting player — this is domain validation, same principle as
`MoveValidator` in the game engine: don't trust client-supplied IDs without
checking ownership server-side.

## Matchmaking

### `POST /api/matchmaking/quick-match`

No body. `202 Accepted`, empty `data`. The actual pairing result doesn't
come back in this response — it arrives later as a `MatchFoundEvent` over
WebSocket. This endpoint just confirms the player entered the queue.

### `POST /api/matchmaking/room/create`

No body.

```json
// response 201  (RoomCreateResponse)
{ "roomCode": "X7K9P2", "expiresAt": "2026-07-18T12:35:00Z" }
```

### `POST /api/matchmaking/room/join`

```json
// request  (RoomJoinRequest)
{ "roomCode": "X7K9P2" }
```

`200` if the join succeeds (pairing confirmed over WebSocket, same as
Quick Match). `404` if the code doesn't exist or already expired. `409` if
the room already has a second player — this is the Lua-script atomic check
from `DATABASE.md`/`ARCHITECTURE.md` §9 actually surfacing as an HTTP
status.

## WebSocket

### Connection & subscriptions

```
CONNECT     /ws/game                  Authorization header carries the JWT, validated once at handshake
SUBSCRIBE   /topic/game/{gameId}      broadcast channel, both players in this game subscribe
SUBSCRIBE   /user/queue/game          private channel — matchmaking results, personal errors, reconnect snapshots
```

### Outbound (client → server)

**`SEND /app/game/move`**

```json
// MoveRequest
{ "gameId": "uuid", "stateVersion": 4, "cardId": "uuid", "stat": "ATTACK" }
```

`stateVersion` must match the session's current version or the move is
rejected as stale — see `ARCHITECTURE.md` §6.

**`SEND /app/game/ready`**

```json
{ "gameId": "uuid" }
```

Signals the client has loaded the initial hand and is ready for the coin
toss / first turn.

### Inbound (server → client) — every event carries a `type` discriminator

The client switches on `type`; these map directly to the sealed `GameEvent`
hierarchy in `game/event/` (plus `MatchFoundEvent` from `matchmaking/event/`).

**`MatchFoundEvent`** — on `/user/queue/game`, once matchmaking pairs you

```json
{
	"type": "MATCH_FOUND",
	"gameId": "uuid",
	"opponentUsername": "gaara_of_the_desert"
}
```

**`GameStartEvent`** — on `/topic/game/{id}`, once both players are ready

```json
{
	"type": "GAME_START",
	"gameId": "uuid",
	"yourHand": [
		{
			"cardId": "uuid",
			"name": "Naruto Uzumaki",
			"attack": 92,
			"defense": 70,
			"chakra": 98,
			"speed": 85
		}
	],
	"firstTurnPlayerId": "uuid",
	"stateVersion": 0
}
```

`yourHand` is the lightweight `CardRef` shape from `game/engine/CardRef.java`
— never the full `Card` entity.

**`TurnEvent`** — turn begins

```json
{
	"type": "YOUR_TURN",
	"stateVersion": 1,
	"turnStartedAt": "2026-07-18T12:40:00Z",
	"turnDeadline": "2026-07-18T12:40:30Z"
}
```

(`type` is `OPPONENT_TURN` on the other player's socket for the same event.)

**`RoundResultEvent`** — after both cards revealed

```json
{
	"type": "ROUND_RESULT",
	"roundNumber": 1,
	"attackerCard": {
		"cardId": "uuid",
		"name": "Naruto Uzumaki",
		"attack": 92,
		"defense": 70,
		"chakra": 98,
		"speed": 85
	},
	"defenderCard": {
		"cardId": "uuid",
		"name": "Gaara",
		"attack": 80,
		"defense": 95,
		"chakra": 88,
		"speed": 40
	},
	"chosenStat": "ATTACK",
	"attackerValue": 92,
	"defenderValue": 80,
	"winnerId": "uuid",
	"stateVersion": 2
}
```

`winnerId` is `null` on a tie.

**`TimerWarningEvent`**

```json
{ "type": "TIMER_WARNING", "secondsRemaining": 10 }
```

**`TimerExpiredEvent`**

```json
{ "type": "TIMER_EXPIRED", "forfeitedRoundNumber": 3 }
```

**`ConnectionStatusEvent`**

```json
{ "type": "OPPONENT_DISCONNECTED", "gracePeriodSeconds": 30 }
```

```json
{ "type": "OPPONENT_RECONNECTED" }
```

**`GameOverEvent`**

```json
{
	"type": "GAME_OVER",
	"winnerId": "uuid",
	"finalScore": { "player1Cards": 6, "player2Cards": 4 },
	"xpEarned": 25
}
```

**`GameStateDTO`** — sent on `/user/queue/game` immediately after a
reconnect, not a "type"-tagged event, a full snapshot instead

```json
{
	"gameId": "uuid",
	"status": "IN_PROGRESS",
	"yourHand": [/* CardRef[] */],
	"opponentCardCount": 4,
	"yourWonPileCount": 2,
	"opponentWonPileCount": 1,
	"currentRound": 4,
	"stateVersion": 6,
	"isYourTurn": true,
	"turnDeadline": "2026-07-18T12:44:10Z"
}
```

Note it sends `opponentCardCount`, not the opponent's actual hand — the
opponent's specific cards are never revealed to you before a round
resolves, same trust-boundary principle as everywhere else.

## Shared shapes referenced above

- **`ApiResponse<T>`** — `{ success, data, error }`, every REST response.
- **`PageResponse<T>`** — `{ content, page, size, totalElements, totalPages }`.
- **`ErrorResponse`** — `{ code, message }`, the `error` field's shape.
- **`CardRef`** — `{ cardId, name, attack, defense, chakra, speed }`, the
  in-memory/wire-format lightweight card, distinct from the full `Card`
  JPA entity — see `ARCHITECTURE.md` §5.
