# Naruto Card Clash — Backend Architecture

This is the architectural reasoning behind the structure in `BACKEND-SETUP.md`
— what patterns are applied, why, and how the pieces fit together as one
system. Not a repeat of the phase list, not a repeat of the topic map in
`LEARNING-TOPICS.md` — this is the "how would you draw this on a whiteboard
and defend every line" document.

---

## 1. Architectural Style

**Modular monolith, not microservices.** Single deployable Spring Boot app;
module boundaries enforced by package convention (`auth/`, `player/`,
`card/`, `matchmaking/`, `game/`, `websocket/`, `leaderboard/`, `common/`),
not by network calls.

Why not microservices: several operations need to be atomic across what
would be separate services (register + grant starter deck must both succeed
or both roll back). Splitting that across services means distributed
transactions or eventual consistency for something that's naturally a single
transaction today. Microservices buy independent scaling and independent
deployment — not a real need at this scale, and the cost (network calls,
service discovery, distributed tracing) isn't worth paying for a
single-team project.

**Package-by-feature, not package-by-layer.** Each module folder contains
its own `controller/`, `service/`, `repository/`, `entity/`, `dto/` — not
one giant `controllers/` folder for the whole app. Trade-off: better
cohesion and discoverability (everything about matchmaking lives in one
place) at the cost of Java not enforcing the boundary at compile time —
nothing stops `game/` from reaching into an internal class inside
`matchmaking/`. That's convention, not a compiler guarantee, unless you
later adopt the Java Platform Module System.

## 2. Layered Architecture (inside every module)

```
Controller   REST or WebSocket entry point
   |  DTO in, DTO out — never an entity
   v
Service      Business logic, @Transactional boundary
   |
   v
Repository   Spring Data JPA — talks to Postgres
   |
   v
Entity       JPA-mapped domain object
```

- Controllers never receive or return entities — only DTOs. This boundary
  keeps persistence details (lazy collections, Hibernate proxies) out of
  the API contract.
- Services own the `@Transactional` boundary. A controller method is never
  itself `@Transactional`.
- Entity <-> DTO mapping happens in the service layer or a dedicated mapper —
  not in the controller.

## 3. Communication Architecture — two protocols, deliberately

| Concern                                    | Protocol        | Why                                                                                                                |
| ------------------------------------------ | --------------- | ------------------------------------------------------------------------------------------------------------------ |
| Auth, profile, card catalog, match history | REST (HTTP)     | Request-response, stateless, cacheable, fits CRUD naturally                                                        |
| Live battle (moves, round results, timers) | WebSocket/STOMP | Server-initiated push is required — you can't poll for "opponent moved" without wasting requests or adding latency |

Not WebSocket-only: you'd lose HTTP caching, standard REST tooling, and
trivial stateless scaling for the parts of the app that don't need
real-time push. Not REST-only with polling: fast polling wastes requests,
slow polling feels laggy — WebSocket is the right tool once you have a
sub-second latency requirement.

## 4. Data Architecture — polyglot persistence

| Store      | Role                                                                                     | Consistency model                                                                                     |
| ---------- | ---------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| PostgreSQL | System of record — players, cards, match history                                         | Strong (ACID)                                                                                         |
| Redis      | Fast, mostly-ephemeral layer — cache, matchmaking queue, active-game backup, leaderboard | Mixed: strong where it must be (`SETNX`, Lua scripts), eventual where staleness is fine (leaderboard) |

Rule underlying this split: **Redis is never the sole source of truth for
anything durable.** Card data is a cache of Postgres data. The matchmaking
queue and rooms are reconstructable ephemeral state. Leaderboard scores are
a derived index, rebuildable from `players.total_wins`. Nothing lives only
in Redis that you couldn't afford to lose.

## 5. State Ownership Architecture — the core Game Engine decision

Active games live in two places at once, for different reasons:

```
Hot path (per move)     In-memory GameSession inside GameSessionManager
                         (ConcurrentHashMap<UUID, GameSession>)
                         — microsecond read/write, zero I/O

Cold path (durability)  Postgres games + game_rounds tables
                         — written at game end (or per round), survives
                           a server restart
```

Not full CQRS, but the same underlying idea: the data you need instantly
(whose turn, what's in each hand) is optimized separately from the data
you need to keep forever (match history feeding the leaderboard/profile).

Consequence you own: if the server crashes mid-game, in-memory
`GameSession` state is gone unless you've been writing a Redis snapshot as
backup — that's the crash-recovery role Redis plays here, distinct from its
cache/queue roles (see `BACKEND-SETUP.md` Phase 7).

## 6. Concurrency & Consistency Architecture

**Single-writer-per-game invariant.** Only one thread is ever allowed to
mutate a given `GameSession`, enforced by one lock per session. This single
rule is what makes the rest of the concurrency story tractable — there's no
cross-session locking, so there's no lock-ordering problem, so deadlock is
structurally impossible here, not just unlikely.

**Optimistic versioning, applied at two layers, same pattern:**

| Layer                | Mechanism                                              | Guards against                                      |
| -------------------- | ------------------------------------------------------ | --------------------------------------------------- |
| In-memory session    | `stateVersion` int, incremented on every accepted move | Stale, duplicate, or late moves                     |
| Postgres `games` row | JPA `@Version`                                         | Lost updates from concurrent writes to the same row |

Same idea twice on purpose — one mental model ("reject anything that
doesn't match the version I expect") instead of two different concurrency
strategies to hold in your head.

## 7. Security Architecture

**Trust boundary:** everything the client claims — "it's my turn," "I own
this card," "I chose ATTACK" — is untrusted input. The server re-derives
ground truth from its own state on every move. This is the single most
important security rule in the game engine: _validate against server
state, never against client-supplied claims._

**Defense layers, in the order a request passes through them:**

```
1. Transport          HTTPS, terminated at a reverse proxy in prod — not app code
2. Authentication      JwtAuthFilter — valid, unexpired, non-blacklisted token?
3. Authorization       @PreAuthorize / route rules — allowed to hit this endpoint?
4. Input validation    @Valid / Bean Validation — is the request well-formed?
5. Domain validation   Service-layer checks against real state — is this move legal right now?
```

Each layer catches a different class of problem; none substitutes for the
others. Bean Validation confirming `cardId` isn't null tells you nothing
about whether the player actually owns that card — that's layer 5.

## 8. Caching Architecture

Redis plays several distinct architectural roles here — worth being
explicit these are different patterns, not "Redis does one thing":

| Role                         | Pattern                             | Example                                        |
| ---------------------------- | ----------------------------------- | ---------------------------------------------- |
| Cache                        | Cache-aside                         | Card catalog (`@Cacheable`)                    |
| Queue                        | Producer-consumer                   | Matchmaking (`LPUSH` / `RPOP`)                 |
| Distributed lock             | Mutual exclusion via atomic `SETNX` | Idempotency guard on double Quick Match clicks |
| Ordered index                | Sorted Set                          | Leaderboard                                    |
| Ephemeral key-value with TTL | Expiring state                      | Private room codes                             |

In a larger system these might live on separate infrastructure (a real
message broker for queueing, a dedicated cache cluster). Here, one Redis
instance wearing five hats is a reasonable simplification — know that it's
a simplification, not a law of nature.

## 9. Queueing / Matchmaking Architecture

```
Client clicks Quick Match
   -> SETNX idempotency lock
   -> LPUSH matchmaking:queue {playerId}
   -> 202 Accepted, client waits on WebSocket

@Scheduled(fixedDelay = 2000) poller
   -> RPOP two players when >= 2 waiting
   -> create Game, notify both via WebSocket
```

This is **polling**, not a blocking pop (`BRPOP`) or a stream-based
consumer. Trade-off: polling every 2s adds up to 2 seconds of matchmaking
latency in exchange for simplicity — no long-lived blocking connection to
manage. A `BRPOP` consumer or Redis Streams with a consumer group cuts that
latency at the cost of a more complex consumer lifecycle. Starting with
polling is a reasonable choice; know the upgrade path.

## 10. Real-Time Messaging Architecture

```
Spring's in-memory   /topic/game/{id}    broadcast — both players subscribed
STOMP broker         /user/queue/game    private — matchmaking result, personal errors
```

Spring's built-in simple broker relays messages in-process — fine for a
single instance. It does **not** fan out across multiple app instances. To
horizontally scale the WebSocket tier you need either sticky sessions
(route a player to the same instance for the whole game) or an external
relay (RabbitMQ, or Redis Pub/Sub) so instance A can deliver to a player
connected to instance B. Same root cause as the `GameSessionManager`
scaling question in section 11 — state pinned to one instance, wearing two
different hats.

## 11. Scalability Architecture

| Component                                      | Scales horizontally as-is?                            | Why / why not                                            |
| ---------------------------------------------- | ----------------------------------------------------- | -------------------------------------------------------- |
| Auth, Player, Card, Leaderboard REST endpoints | Yes                                                   | Fully stateless — any instance serves any request        |
| Postgres                                       | Vertically, or read replicas for read-heavy paths     | Single writer needed for strong consistency on game data |
| Redis                                          | Yes for cache/queue reads at moderate scale           | Redis Cluster if you outgrow one node                    |
| `GameSessionManager` (in-memory)               | **No**                                                | State pinned to whichever instance holds it              |
| WebSocket broker                               | **No**, without sticky sessions or an external broker | Same root cause as above                                 |

Defensible answer for a project this size: single-instance is correct here,
and the two things that don't scale horizontally (session state, message
broker) share one fix — move the shared state into Redis and let any
instance read/write through it. Have both the "why single-instance is fine
here" answer and the "here's exactly what I'd change" answer ready;
interviewers want the reasoning, not a specific instance count.

## 12. Resilience & Failure Architecture

| Failure                          | Impact                                                                                                                          | Mitigation                                                                                                                                      |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| Postgres down                    | Can't register/login/persist results                                                                                            | None at app level — it's the system of record, a hard dependency by design                                                                      |
| Redis down                       | Card cache misses fall through to Postgres (slower, still correct); matchmaking stops accepting entries; leaderboard reads fail | Cache-aside degrades gracefully; queue/leaderboard don't — Redis is a real single point of failure here, worth naming rather than glossing over |
| App instance crash mid-game      | In-memory `GameSession` lost unless a Redis snapshot exists                                                                     | Periodic snapshot to `game:{id}:state`, replay on restart                                                                                       |
| Player disconnects mid-turn      | Opponent waits indefinitely without handling                                                                                    | Grace-period timer + auto-forfeit on expiry — a resilience pattern, not just UX                                                                 |
| Duplicate request (client retry) | Double room-join, duplicate round row                                                                                           | `SETNX`, `UNIQUE(game_id, round_number)` — retry-safety is a resilience property                                                                |

## 13. Observability Architecture

- **Structured logs** tagged with a `gameId`/`correlationId` on every line
  inside a game flow — without this, debugging a specific match's race
  condition after the fact is close to impossible.
- **Actuator** (`/actuator/health`, `/actuator/metrics`) — baseline
  production health signal.
- **Metrics worth adding**, cheap via Micrometer: `active_games` gauge,
  `matchmaking_queue_depth` gauge, `avg_round_resolution_ms` timer —
  disproportionately useful for showing you think about a system in
  production, not just in a debugger.
- **Out of scope on purpose:** distributed tracing (OpenTelemetry) — only
  pays off once a request crosses more than one service, which this
  project deliberately doesn't have (see section 1).

---

## 14. API Contract Design

- **REST**: nouns for resources (`/api/players`, `/api/cards`), verbs for
  actions, status codes carry meaning (401 vs 403 vs 409 — not everything
  collapsed to 200 or 500).
- **Standard envelope**: every REST response is `ApiResponse<T>` —
  `{ success, data, error }` — one shape for the frontend to parse
  regardless of endpoint.
- **WebSocket event contract**: a fixed, named set of event types
  (`GAME_CREATED`, `YOUR_TURN`, `ROUND_RESULT`, `GAME_OVER`, etc.) — the
  client switches on event type, not on parsing ad hoc message shapes.
- **Versioning**: not implemented, but have a stance ready — URI versioning
  (`/api/v2/...`) is simpler to reason about than header-based content
  negotiation for a project this size.
